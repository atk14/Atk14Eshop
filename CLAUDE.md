# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Lineage

This repository, **Atk14MiniSkelet**, is the base of a chain of ATK14 application skeletons, each building on the previous one: `Atk14MiniSkelet` → `Atk14Skelet` → `Atk14Catalog` → `Atk14Eshop` → actual client applications. Conventions, structure and fixes introduced here flow forward into every one of those. If you're reading this file in a downstream repository, the directory layout, routing conventions, and ATK14 idioms described below originated here and should still apply unless explicitly overridden locally.

This file is itself one of the things that flows downstream, usually via a regular merge from the parent skeleton. Keep that in mind when editing it:
- Describe conventions and mechanisms, not an exhaustive snapshot of current contents (e.g. "the admin nav is built from a declarative `$items` list" rather than "the admin nav has exactly these three entries") — a downstream app's actual controllers, migrations, and models will diverge over time, and the description should keep holding up anyway.
- Add downstream-specific guidance (a real app's business domain, a child skeleton's added features) in new sections rather than rewriting the inherited ones, so merges from upstream stay conflict-free by default.
- If a merge *does* conflict on this file, that's a useful signal that local reality and the upstream description diverged — resolve it by hand and update the wording, don't just take one side automatically.

## What this is

A minimal, runnable ATK14 application ("skeleton") providing just enough to bootstrap a real app: user registration, login/logout, password recovery, a small admin section, and front-end asset tooling (Gulp + BrowserSync). It is not itself a product — it exists to be cloned/forked into real applications. The ATK14 framework itself lives as a git submodule in `atk14/` (https://github.com/atk14/Atk14.git); application code lives alongside it following ATK14's MVC conventions.

## Setup and commands

```bash
git submodule init && git submodule update   # fetch the atk14 framework submodule
composer install
./scripts/create_database
./scripts/migrate
```

After cloning this skeleton to start a new app, run `./local_scripts/update_project_name <appname>` (or with no argument, to infer the name from the current directory name) — it rewrites the `_test`/`_devel`/`_production` db/username suffixes in `config/database.yml` and `ATK14_HTTP_HOST`/`ATK14_APPLICATION_NAME` in `config/settings.php`. This is the actual "fork the skeleton into a real app" step; do it before anything else in a freshly cloned repo.

A seeded admin user (`login: admin`, `password: admin`, `is_admin = true`, id 1) exists after migrations (`db/migrations/0001_users.sql` + `0002_reset_admins_password_migration.php`) — use it to sign in to `/admin/` locally. `RemoteTestsController::admin_default_password()` (see below) exists specifically to fail a production health check if this default password was never changed.

Run the dev server: `./scripts/server` (defaults to `http://localhost:8000/`, optional port/address as first arg).

Front-end assets (Gulp):
```bash
npm install -g gulp && npm install
gulp && gulp admin        # initial build of public site + admin assets
gulp serve                # serve/watch public site assets with BrowserSync
gulp lint                 # ESLint for public site JS (gulpfile.js)
gulp lint-admin           # ESLint for admin JS (gulpfile-admin.js)
```

Database:
```bash
ATK14_ENV=test ./scripts/create_database
ATK14_ENV=test ./scripts/migrate         # applies pending db/migrations/* (.sql or .php)
./scripts/migrate --list                 # list migrations / status
./scripts/dbconsole                      # open a DB console for the current env
./scripts/dump_db                        # dump schema + data (backup); ATK14_ENV=PRODUCTION ./scripts/dump_db -t users for one table
./scripts/dump_dbschema                  # dump schema only
echo 'y' | ATK14_ENV=test ./scripts/destroy_database_objects && ATK14_ENV=test ./scripts/migrate  # wipe and recreate the test db (DEVELOPMENT/TESTING env only)
```

Tests (ATK14's own tester, not PHPUnit):
```bash
./scripts/run_all_tests                  # runs every test/* directory containing initialize.php
cd test/controllers && ../../scripts/run_unit_tests tc_users       # run one test file (TcUsers in tc_users.php)
cd test/models && ../../scripts/run_unit_tests tc_application_model tc_invalid_password_attempt  # run a few
```
`run_all_tests` auto-applies pending `ATK14_ENV=TEST` migrations before running. Test suites live under `test/{app,controllers,controllers/admin,controllers/api,models,fields,helpers,lib}`, each with its own `initialize.php`. A test case file `tc_foo.php` must define a class `TcFoo`.

Fixtures (`test/fixtures/*.yml`, see `test/fixtures/README.md`) seed test data declaratively — a YAML file named e.g. `users.yml` defines named records (`rambo:`, `rocky:`, …) for model `User`. A test case opts in via a `@fixture` docblock annotation (one per line for multiple fixtures) and gets the loaded records as `$this->users["rambo"]`, etc. — see `test/controllers/tc_logins.php` or `test/fixtures/users.yml` for real examples.

Interactive console (like a Ruby on Rails console — loads the full app environment and models for ad-hoc use):
```bash
./scripts/console
echo '$u = User::FindFirst(); var_dump($u->toArray());' | ./scripts/console   # non-interactive mode
```

Inspect effective configuration:
```bash
./scripts/dump_settings                  # list all application constants
./scripts/dump_settings DEFAULT_EMAIL    # inspect a single constant
./scripts/recognize_route http://atk14miniskelet.localhost/some/path/   # see which route/controller/action matches a URI
```

Background jobs (`robots/`, see `robots/README.md`): classes `FooRobot extends ApplicationRobot` (e.g. `sessions_cleanup_robot.php`, `vacuum_analyze_robot.php`, `invalid_password_attempts_cleanup_robot.php`) run via the framework's `./scripts/robot_runner <name>`, accepting the name in several forms (`sessions_cleanup`, `sessions_cleanup_robot`, `SessionsCleanupRobot`, …). In production these are wired into cron via `local_scripts/robots_regular|robots_daily|robots_weekly` (each just a list of `./scripts/robot_runner ...` calls) — see `local_scripts/README.md` for the example crontab. Robots take out lock files in `robots/lock/`; `RemoteTestsController::stale_locks()` monitors those for staleness. Don't confuse this `robots/` directory with `test/` — it has nothing to do with testing.

Deployment, driven by `config/deploy.yml` (per-stage server/user/directory, `before_deploy`/`after_deploy` hooks, rsync paths):
```bash
./scripts/deploy              # deploy to the first stage in config/deploy.yml (production)
./scripts/deploy production
./scripts/deploy preview      # any other stage defined in config/deploy.yml
./scripts/deploy -l           # list available stages
```

## Architecture

**Request flow:** `public/index.php` → `dispatcher.php` → `atk14/load.php` boots the framework → `Atk14Dispatcher::Dispatch()` resolves the request through the routers in `config/routers/load.php`, then instantiates the matched `*_controller.php` under `app/controllers/`.

**Routing (`config/routers/`):** Routers are plain PHP classes autoloaded by filename (class `FooBarRouter` ↔ file `foo_bar_router.php`), registered in `config/routers/load.php` in the order they should be tried:
- `AdminRouter` (`admin_router.php`) — namespace `"admin"`, currently empty; add admin-specific SEF routes here.
- `ApplicationRouter` (`application_router.php`) — namespace `""`; hand-written, search-engine-friendly routes (`/sign-in/`, `/sign-up/`, `/recovery/<token>`, sitemap/robots routes, etc.). Add new human-friendly URLs here, in order, before the generic fallback.
- `GenericRouter` (`generic_router.php`) — **must stay last**. Provides the catch-all patterns every ATK14 app needs: `/`, `/<lang>/`, `/<lang>/<controller>/`, `/<lang>/<controller>/<action>/`. Don't add specific routes here; add them to `ApplicationRouter` (or a namespace-specific router) instead, since routers are matched in registration order.

**Controllers (`app/controllers/`):** `ApplicationBaseController` (extends `Atk14Controller`) holds cross-cutting concerns (breadcrumbs, `error404`/`error403`, before/after filter wiring, transaction begin/end). `ApplicationController` extends it for the public namespace. Namespaced controllers live in subdirectories matching the router namespace, e.g. `app/controllers/admin/`, `app/controllers/api/`.

`admin/admin.php` defines `AdminController`, the base for all admin-namespace controllers (`main_controller.php`, `users_controller.php`, `password_recoveries_controller.php`, …). Its `_application_before_filter()`:
- enforces `logged_user->isAdmin()`, redirecting anonymous users to login;
- builds the admin section navigation (`Menu14`) and breadcrumbs from a declarative `$items` list of `[label, target]` pairs. `target` may be a bare controller name (implies `.../index`), an explicit `"controller/action"` string, a comma-separated list of controllers sharing one nav entry, or an absolute path starting with `/` (used verbatim, never marked "active" since it has no corresponding controller). See the code comments there before changing this logic — the leading-slash check exists specifically to avoid `strpos() === 0` being falsy in PHP.

`RemoteTestsController` (`app/controllers/remote_tests_controller.php`) is an HTTP health-check endpoint for external monitoring (e.g. Nagios), not a test suite despite living next to `test/`: each public method returns HTTP 200 (pass) or 500 (fail) via `_assert_true()`/`_fail()`, and `index()` lists all of them by reflecting on its own source. Existing checks include `disk_space`, `stale_locks` (robots/lock/ freshness, see Background jobs above), and `admin_default_password` (fails if the seeded admin/admin login still works — see Setup above).

CRUD-heavy admin controllers mix in `TraitCrudActions` (`app/controllers/trait_crud_actions.php`) for generic `_index`/`_create_new`/etc. helpers driven by an `$options` array (`class_name`, `searching_in`, `sorting_by`, `conditions`, …) rather than reimplementing listing/search/sort per controller.

**Views (`app/views/<namespace or controller>/`), layouts (`app/layouts/`), helpers (`app/helpers/`):** Smarty-based (`.tpl`). Custom Smarty blocks/functions/modifiers live in `app/helpers/` as `block.*.php`, `function.*.php`, `modifier.*.php` (e.g. `function.admin_menu.php` renders the per-object admin dropdown menu used across detail views). `app/layouts/admin/` and `app/layouts/rest_api/` hold layout variants for those namespaces.

**Models (`app/models/`):** Plain ActiveRecord-style classes extending `Atk14` conventions; shared behaviors are implemented as traits/mixins (`translatable.php`, `rankable.php`, `trait_get_instance_by_code.php`) rather than deep inheritance.

Two distinct password-hashing mechanisms coexist, don't confuse them: `User` hashes its login password via `MyBlowfish::Filter()` (package `yarri/my-blowfish`, requires the `CRYPT_BLOWFISH` PHP flag asserted in `config/requirements.yml`) transparently inside `setValues()`/`CreateNewRecord()`, checked via `User::isPasswordCorrect()`; one-time passwords (`app/models/one_time_password.php`, used for recovery/2FA-style flows, scoped by `purpose` + `object_key`) instead hash via PHP's own `password_hash()`. Brute-force login throttling is `InvalidPasswordAttempt::IsRemoteAddressBlocked($ip)` — an exponential-backoff lockout (5 attempts allowed per round, 5–60 min escalating delay, 2h lookback window; `MAX_INVALID_LOGIN_ATTEMPTS` setting) — reused for any `purpose`/`object_key`-scoped throttling, not just the login form.

Custom form fields (`app/fields/`) follow ATK14's `*Field extends ...Field` convention. Notably `ObjectField` (base for `UserField`, etc.) auto-derives both the related model class (`UserField` → `User`) and an autocomplete suggestion endpoint (`UserField` → `api/suggestions/users`) purely from the field's own class name; the matching controller side is the shared `_suggest()` helper in `app/controllers/api/suggestions_controller.php`. To add an autocomplete picker for a new model, this is the pair of places to touch.

**Mailer (`app/controllers/application_mailer.php`, `app/views/mailer/*.tpl`):** one method per email, e.g. `notify_user_registration($user)` sets `to`/`subject`/`tpl_data` and implicitly renders `app/views/mailer/notify_user_registration.html.tpl` (called via `$this->mailer->notify_user_registration($user)`, proxied through `Atk14MailerProxy`). In `DEVELOPMENT`, mail is logged instead of actually sent. `_after_render()` auto-derives the plain-text body from the HTML body via `Html2Text` when no explicit plain body was set, stripping anything wrapped in `<!-- header -->…<!-- /header -->` / `<!-- footer -->…<!-- /footer -->` HTML comments first.

**Database (`db/migrations/`, `config/database.yml`):** Numbered, sequentially-applied `.sql` or `.php` migration files (`0001_users.sql`, `0002_reset_admins_password_migration.php`, …). `zz01`/`zz02` suffixes mark later, corrective migrations against an earlier-numbered one. `application_migration.php` is the shared base class for PHP migrations. `config/database.yml`'s `production` password is not a plaintext committed secret but a PHP expression evaluated at load time (`<?=sha1(SECRET_TOKEN."...")?>`) — the pattern for deriving production secrets from `SECRET_TOKEN` instead of committing them.

**i18n (`config/locale.yml`, `locale/`):** Supported languages and the default one are declared in `config/locale.yml` (first entry = default; `fallback` lets one language inherit translations from another). Routes carry a `<lang>` segment (see `GenericRouter`); `$this->default_lang` is available in router `setUp()`.

**Settings (`config/settings.php`):** Application-wide constants via `definedef(...)` (define-if-not-already-defined), including feature toggles like `USER_REGISTRATION_ENABLED`, `INVITATION_CODE_FOR_USER_REGISTRATION`, `USING_BOOTSTRAP4`. Framework defaults are in `atk14/default_settings.php`; use `./scripts/dump_settings` rather than grepping both files.

**Local overrides (`local_config/`):** Everything under `local_config/` is gitignored (not version-controlled) — it's per-environment/per-developer config. A file here (e.g. `local_config/settings.php`) takes precedence over the same-named file in `config/` (`atk14/load.php` loads `local_config/settings.php` instead of `config/settings.php` when it exists). The convention is to end `local_config/settings.php` with `require(__DIR__ . "/../config/settings.php");` so local overrides layer on top of (before) the tracked defaults rather than replacing them entirely.

**REST API (`app/controllers/api/`, `app/controllers/application_rest_api.php`, `app/forms/api/`, `app/views/shared/rest_api/`):** A separate namespace/layout for JSON endpoints, following the same controller/form conventions as the HTML side. `ApplicationRestApiController` auto-generates human-readable docs per action from doc-comments; set `$doc_basic_auth` (string `"user:pass"` or an array keyed by regex) on a controller to put that generated documentation behind HTTP basic auth — separate from whatever auth the actual API endpoints use.

**Error reporting (`lib/load.php`):** when the Tracy library is available and not in the `TEST` env or CLI, `Tracy\Debugger::enable(PRODUCTION, log/, …)` is wired up — in production, uncaught PHP errors/exceptions are logged under `log/` and emailed to `ATK14_ADMIN_EMAIL` (`config/settings.php`); outside production Tracy's debug bar is shown instead. `lib/` is also where small non-Composer helper libraries (e.g. `lib/head_tags/`) and the Composer autoloader itself get required from.

**Forms (`app/forms/`):** One form class per controller action pattern (`app/forms/users/create_new_form.php`-style), mirroring the `app/controllers/` namespace layout; `application_form.php` / `rest_api_form.php` are the shared base classes.

## Content & media layer (added in Atk14Skelet)

On top of the bare MiniSkelet, this skeleton adds a small CMS-ish layer — hierarchical pages, articles, tags, media and newsletter sign-up — plus the generic mechanisms that tie them together. These flow downstream the same way the rest of this file does, so describe mechanisms here, not the specific content models a given app ends up with.

**Pages (`app/models/page.php`, `config/routers/pages_router.php`):** `Page` is a self-referencing tree (`getParentPage()`/`getRootPage()`), addressed by per-segment slugs rather than ids — `Page::GetInstanceByPath("company/management")` walks the slug chain. `PagesRouter` recognizes any otherwise-unmatched top-level path as a candidate page path and resolves it to `pages/detail`; on `build()` it reverses the mapping back to `/<path>/`, special-casing the page coded `"homepage"` to link to `main/index` instead of a literal path. Because it treats any unrecognized URL as "maybe a page", `PagesRouter` must be registered early (see `config/routers/load.php`) but still after routers that own more specific namespaces.

**Articles (`app/models/article.php`, `config/routers/articles_router.php`):** a simple blog-style content type (`ArticlesRouter extends SluggishRouter`, per-language `index`/`detail` URL patterns) — the pattern to copy for any other flat, non-hierarchical content listing.

**Iobject / IobjectLink (`app/models/iobject.php`, `iobject_link.php`):** the polymorphic "pluggable content object" pattern. Any model can extend `Iobject` (e.g. `Gallery`, `Video`, `Picture`) to become a first-class, independently editable record that can also be *linked* into other objects' bodies — `Gallery::CreateNewFor($article, [...])` creates-and-links in one call, `Iobject::GetInstancesFor($article)` (or the subclass-typed `Gallery::GetInstancesFor($article)`) reads them back ordered by an explicit rank stored on `IobjectLink`. An iobject can be dropped inline into markdown/rich-text content via its insert mark (`$iobject->getInsertMark()`, e.g. `[#123 Gallery: Holiday photos]`); rendering back to HTML goes through `function.iobject_to_html.php`, dispatched by `getObjectType()` (derived from the iobject's own `referred_table` column, not a stored type flag). Don't confuse this with `LinkedObject` below — an `Iobject` is a standalone content item that happens to be attachable; a `LinkedObject` only exists as an attachment.

**LinkedObject (`app/models/linked_object.php`):** the simpler sibling — a base for models that only ever exist *attached* to something else (e.g. `Image`, `Attachment`), scoped by `table_name` + `record_id` + an optional free-form `section` string (so one object can hold several independently-ordered groups of attachments, e.g. `Image::GetInstancesFor($product, "secondary_images")`). Implements `Rankable` and keeps a per-request in-memory cache keyed by holder class/table/record, batch-populated across whatever's already in `Cache` for that class to avoid N+1 lookups when rendering a listing.

**Tags (`app/models/tag.php`, `trait_tags.php`, `app/fields/tags_field.php`):** any model can `use TraitTags` to get `getTags()`/`setTags()`/`addTag()`/`containsTag()` backed by a `Lister` (`getTagsLister()`); tags accept a `Tag` instance, a numeric id, or a bare code string interchangeably (`_cleanTag()` resolves whichever was passed). `TagsField` is the matching admin form field — a comma-separated autocomplete input wired to `api/tags_suggestions_controller.php`, with `create_tag_if_not_found` controlling whether typing a new tag name creates it on the fly.

**Media via Pupiq (`app/models/trait_pupiq_image.php`, `trait_pupiq_attachment.php`, the `atk14/pupiq-client` package, `PUPIQ_API_KEY`/`PUPIQ_HTTPS` settings):** `Image`/`Picture`/`GalleryItem` mix in `TraitPupiqImage` to delegate URL-building and resizing to the Pupiq remote image-processing service instead of serving raw uploaded files — `$image->getUrl("80x80")`/`getWidth()`/`getHeight()` take a transformation string and fall back to the original `_getUrl()` when Pupiq has nothing to serve yet. `ARTICLE_BODY_MAX_WIDTH` is the default transformation used when none is given, since most image rendering happens inside article/page bodies. The matching admin-side upload widgets live in `app/widgets/` (`pupiq_image_input.php`, `async_pupiq_attachment_input.php`, …) and `app/fields/` (`pupiq_image_field.php`, `async_pupiq_attachment_field.php`) — `async_*` variants upload out-of-band via `TEMPORARY_FILE_UPLOADS_*` settings before the surrounding form is submitted.

**Widgets (`app/widgets/`):** a new directory alongside `app/fields/` for reusable form *input* rendering (the HTML widget a field uses), as distinct from a field's validation/cleaning logic — split out when a widget (e.g. an async-upload input) is reused across more than one field.

**Markdown content (`app/helpers/modifier.markdown.php`, `block.markdown.php`, the `atk14/drink-markdown` package):** page/article bodies are authored in Markdown and rendered via `{$body|markdown}` / `{markdown}...{/markdown}`, backed by `DrinkMarkdown` with `iobjects_processing_enabled` (resolves `[#123 ...]` insert marks, see Iobject above) and `shortcodes_enabled`. Shortcodes are bbcode-like blocks (`<!-- drink:tabs -->`, `:collapse`, `:col`/`:row`, `:person(s)`, `:linklist`) each implemented as a `block.drink_shortcode__<name>.php` Smarty block rendering a `shared/helpers/drink_shortcodes/_<name>.tpl` partial — add a new shortcode by adding that pair. `api/markdown_controller.php`'s `transform` action (routed via `MarkdownManualRouter`) exposes the same rendering as a JSON endpoint, used for live preview in the admin Markdown editor; it's admin-only (`_logged_admin_required()`).

**Custom 404 redirects (`app/models/error_redirection.php`):** `ApplicationBaseController` (see `application_base.php`) consults `ErrorRedirection::GetInstanceByHttpRequest($this->request)` on any non-XHR GET that would otherwise 404, matching the longest literal `source_url` (or, for rows with `regex=TRUE`, a regex) and redirecting instead of rendering `error404`. This is the place to look when a client asks for "redirect old URL X to new URL Y" — it's admin-editable data, not a router change.

**Newsletter sign-up (`app/models/newsletter_subscriber.php`, `newsletter_subscription_request.php`, `config/routers/newsletter_subscriptions_router.php`, `SIGN_UP_FOR_NEWSLETTER_ENABLED` setting):** a double opt-in flow — `NewsletterSubscriptionRequest` is created on sign-up and emailed a confirm token; confirming promotes it to a real `NewsletterSubscriber`. Unsubscription mirrors the same create-request → email-confirm shape (`NewsletterSubscribeDeletionRequest` → destroys the `NewsletterSubscriber`). All of it is routed per-language directly in `NewsletterSubscriptionsRouter` rather than `ApplicationRouter`, since every step (sign-in, sent, confirm, sign-out, destroyed) needs a URL in every supported language.

## Product catalog layer (added in Atk14Catalog)

On top of the content layer inherited from Atk14Skelet, this skeleton adds the actual e-commerce catalog: products organized into a category tree, brands, collections, physical stores, and the generic mechanisms (slugs, card sections, technical specifications) that tie them together. As with the rest of this file, describe the mechanisms here, not the specific categories/brands a given downstream app ends up with.

**Card vs. Product:** a `Card` (`app/models/card.php`) is the sellable "thing" as presented in the catalog — its name, teaser, images, category placement, related/accessory/consumable cards; a `Product` (`app/models/product.php`) is one purchasable variant of a card (e.g. a size or color), identified by its own `catalog_id` and optionally a `label` ("XL", "50g"). A card with exactly one product behaves as a non-variant product (`Card::hasVariants()`/`canBeSwitchedToNonVariantMode()` gate the admin UI around this); `Product::getName()` falls back to the parent card's name plus its own label when the product has no name of its own. Soft-deleting either (`destroy()` without `$delete_for_real`) sets `deleted=true` rather than removing the row — a deleted product's `catalog_id` gets a `~deleted-<id>` suffix so the original id can be reused, and `Product::GetInstanceByCatalogId()` strips that suffix back off when looking up a deleted product by its original catalog id.

**Category tree (`app/models/category.php`, admin `category_trees_controller.php`):** `Category` is a self-referencing tree like `Page` (see Pages above), but addressed by id/path rather than by code, and with two extra wrinkles: a category can be an *alias* (`pointing_to_category_id` set, `isAlias()`/`isPointingToCategory()`) that transparently redirects card listings and URLs to another "real" category (`realMe()`/`realMeId()`), used to expose the same branch of cards under more than one path without duplicating data; and a category can be a *filter* (`is_filter`), meaning its children aren't sub-categories but filter *values* (e.g. a "Color" filter category with "Red"/"Blue" child categories) — `Card::getActiveFilters()`/`getCategories(["filters_only" => true])` and `Category::getAvailableFilters()` separate real category membership from filter-value membership, and `allowProducts()`/`allowSubcategories()`/`canBeAliased()` encode which combinations are forbidden (e.g. you can't alias a filter, or add products directly to a filter category). `Card::GetFinderForCategory($category, $filter_d)` is the main catalog listing/search query builder — it walks the category's full branch (`getBranchCategoryIds()`) and applies brand/designer/collection/filter conditions derived from query-string params; this is the place to extend when adding a new faceted-search dimension.

**Slugs (`app/models/slug.php`, `i_slug.php`):** a reusable SEO-slug mechanism, distinct from `Page`'s own per-segment slug column — any model can implement `iSlug` (`getSlugPattern($lang)`, `getSlugSegment()`) to get one row per language in the shared `slugs` table (`table_name` + `record_id` + `lang` + `segment`), with automatic collision handling (`Slug::_BuildSlug()` appends a numeric suffix, falling back to `uniqid()` past 50 collisions) and a generic fallback slug (`<table>-<lang>-<id>`) for objects that don't have a real one yet. `segment` exists so the same slug text can be reused across independent groups of objects sharing one table — `Category` scopes it by `parent_category_id` so sibling categories in different branches can reuse a name. `Card`, `Category`, `Brand`, `Collection`, and `Store` all implement `iSlug`; `CardsRouter extends SluggishRouter` while `CategoriesRouter` is hand-written (recognizing/building multi-segment category paths via `Category::GetInstanceByPath()`/`GetInstancesOnPath()`) since a category's URL has to walk its whole ancestor chain rather than a single slug segment.

**Brands, Collections, Stores (`app/models/brand.php`, `collection.php`, `store.php`):** simpler, flat (non-hierarchical) catalog entities, each `Translatable`, `Rankable` and `iSlug`, each with its own router (`brands_router.php`, `collections_router.php`, `stores_router.php`) following the `CardsRouter` pattern. A `Collection` additionally enforces that a card belongs to at most one collection at a time (`Collection::addCard()` throws `SingleCollectionException` otherwise); `Card::setCollection()` is the usual way to change it since it transparently removes the card from any previous collection first.

**Card sections (`app/models/card_section.php`, `card_section_type.php`):** a card's detail-page body isn't a single field but an ordered (`Rankable`) list of typed, translatable sections (e.g. "information", "tech_spec" — `CardSectionType` is the small, admin-editable lookup table of allowed types, resolved via `TraitGetInstanceByCode`), each able to carry its own images/attachments/embedded videos. `Card::hasCardSection($type_code)`/`getCardSections()` are how views and other code check what's present rather than assuming a fixed layout.

**Technical specifications (`app/models/technical_specification.php`, `technical_specification_key.php`):** an EAV-style key/value mechanism for per-card specs (e.g. "Weight" → "1.2 kg") — `TechnicalSpecificationKey` is the shared, admin-managed, translatable set of possible keys (`GetOrCreateKey()`/`GetInstanceByKey()` resolve a key by its non-localized code, case-insensitively), `TechnicalSpecification` is the per-card value row (translatable `content`, `Rankable` within the card). `Card::getTechnicalSpecification($key)` accepts a code string, a numeric id, or a `TechnicalSpecificationKey` instance interchangeably. Values are read through a request-scoped `CacheSomething` batch-loader (`TechnicalSpecification::GetInstancesForCard()`) to avoid N+1 queries when rendering a card listing.

**Bridge-table admin controllers (e.g. `app/controllers/admin/category_cards_controller.php`, `collection_cards_controller.php`, `related_cards_controller.php`, `category_recommended_cards_controller.php`):** the recurring pattern for managing a `Lister`-backed many-to-many relation (category↔card, card↔related-card, etc.) in the admin: a dedicated controller named after the join table, scoped to the owning record via `_before_filter()`'s `_find()` calls, exposing `create_new`/`set_rank`/`destroy` against the owning model's `getXxxLister()`/`addXxx()`/`removeXxx()` methods rather than operating on the join table directly. Copy this shape (not `TraitCrudActions`) when adding a new many-to-many relation that needs its own rank and admin UI.

**Link lists (`app/models/link_list.php`, `link_list_item.php`, `trait_url_params.php`):** an admin-editable, code-addressable (`TraitGetInstanceByCode`) ordered list of links, used to build auxiliary navigation (footer columns, mega-menu submenus) without a code deploy. Each `LinkListItem` stores its target as a raw URL but `TraitUrlParams` additionally parses it (via `Atk14Url` recognition) into `url_params`, letting `getTargetObject()`/`getSubmenu()` detect "this link points at a `Page`/`Category`/the brands index" and auto-generate a submenu from that target's children instead of requiring the editor to hand-build one. `LinkList::asSubmenu()` renders the whole list as a `Menu14`, the same menu abstraction the admin nav itself uses (see `AdminController` above).

## Order, checkout & payment layer (added in Atk14Eshop)

On top of the catalog layer inherited from Atk14Catalog, this skeleton adds the actual commerce transaction: a basket that becomes an order, checkout as a guided funnel, delivery/shipping configuration, payment gateway integrations, the price-resolution engine, discount/voucher/campaign mechanisms, and the supporting features (stock, reviews, favourites, digital downloads, cookie consent) that a real storefront needs on top of a browsable catalog. As with the rest of this file, describe the mechanisms here, not the specific delivery/payment providers a given downstream app ends up wiring in.

**Basket → Order lifecycle:** `BasketOrOrder` (`app/models/basket_or_order.php`) is a shared abstract base class (not a trait) that `Basket` and `Order` both extend — it holds everything symmetric between a not-yet-committed cart and a placed order: currency/VAT math (`getItemsPrice()`, `getCurrencyDecimalsSummary()`), the address-field schema shared by both (`GetAddressFields()`, parameterized by `prefix` so the same field list produces either invoice or `delivery_`-prefixed columns), delivery/payment method accessors, and voucher/campaign discount totals. The per-line-item mirror is `BasketOrOrderItem` (`basket_or_order_item.php`), extended by `BasketItem` and `OrderItem`: it implements price-rounding logic generically but declares four methods (`setRank()`, `_getRawUnitPriceInclVat()`, `_getRawUnitPriceBeforeDiscountInclVat()`, `getVatPercent()`) that throw unless redefined by the subclass — `BasketItem` sources these live from `PriceFinder`/`getProductPrice()` since a basket's prices float with the catalog, while `OrderItem` just reads its own frozen `unit_price_incl_vat`/`vat_percent` columns, since an order is a price snapshot. `BasketOrOrderItems` (an `ArrayObject` subclass) is the shared collection wrapper that prefetches `Product`/`Card` into `Cache` to avoid N+1s when rendering a listing.

**Basket-to-Order conversion (`Basket::createOrder()`):** this is the one place the two diverge into a real transformation rather than parallel structure. It snapshots the basket's current field values, resolves every address getter through the method-name trick `String4::ToObject($key)->camelize()->prepend("get")` so it works uniformly across the address-field list, freezes delivery/payment fee amounts and their VAT rates into plain columns (`delivery_fee_incl_vat`, `payment_fee_vat_percent`, etc.) rather than leaving them to be recomputed later, and copies each `BasketItem` into an `OrderItem` with its already-rounded unit price baked in. A synthetic `price_rounding`-coded `OrderItem` absorbs any penny-level delta between the summed, re-rounded item prices and the basket's own `getPriceToPay()` — `Order::recalculatePriceToPay()` (called after admin edits to order items) maintains/removes this same synthetic line. Vouchers and campaigns are copied into `OrderVoucher`/`OrderCampaign` rows (free-shipping ones specially flagged so they aren't double counted against the frozen shipping fee), a `PaymentTransaction` is created if the payment method has a gateway, and finally `OrderStatus::DetermineNextAutomaticStatus()` may immediately advance the brand-new order past `"new"` (e.g. to `"waiting_for_bank_transfer"` or straight to `"payment_accepted"` if nothing is owed) before `CheckoutsController::summary()` destroys the basket and redirects to `orders/finish`.

**Order status machine (`OrderStatus`, `OrderHistory`, `OrderLabel`):** `OrderStatus` is a `Rankable`/`Translatable` codebook (`TraitGetInstanceByCode`) whose rows carry behavioral flags rather than hardcoding them in PHP — `finished_successfully`/`finished_unsuccessfully`/`finishing_successfully`/`finishing_unsuccessfully`, `reduce_stockcount`, `blocking_stockcount`, `notification_enabled` (gated further by a per-order `custom_notification_enabled` override) — plus a declared, admin-editable graph of `getAllowedNextOrderStatuses()` used both to constrain the admin status-change form and, filtered further in `Order::getAllowedNextOrderStatuses()`, to hide e.g. `"payment_accepted"` for cash-on-delivery orders. `Order::setNewOrderStatus()` is the single mutator: it only accepts a new status if its timestamp is not older than the current one (statuses can arrive out of order from async sources — a payment gateway can jump the status directly while a slower queue later delivers a stale one), appends an `OrderHistory` row, retroactively fixes any later history rows that only recorded a `responsible_user_id` change rather than a real transition, fires `notify_order_status_update` mail when the status actually changed and notifications are enabled, and toggles warehouse stock (`Warehouse::addProduct()`) when crossing a `reduce_stockcount` boundary in either direction. `OrderHistory` rows double as the audit log for both status changes and responsible-user reassignment (`change_status`/`change_responsible_user` booleans distinguish the two). `OrderLabel` is an unrelated, simpler `Rankable`/`Translatable` tag-like codebook for colour-coding orders in the admin list — not part of the status graph.

**Checkout as a stepped funnel (`CheckoutsController`):** each action is one step gated by what the basket already has set, so a user dropped at any URL gets redirected to the right earlier step rather than the controller tracking explicit wizard state: `set_payment_and_delivery_method` → `user_identification` (skipped straight through if already logged in or a delivery address is already present, i.e. guest checkout already chosen) → `set_billing_and_delivery_data` (bounces back if no delivery/payment method yet) → `summary` (bounces back further if the address isn't set, or forward-blocks via `$basket->canOrderBeCreated()`) → `finish`, which forwards to the public `OrdersController::finish` by token. `summary` double-checks a `checksum` hidden field (a hash of product id + amount pairs) against resubmission so a stale page can't silently commit a since-changed basket; on success it calls `$basket->createOrder()`, persists the delivery address used (`DeliveryAddress::GetOrCreateRecordByBasket()`, dedup'd by exact field match) so it resurfaces as a suggestion next time, and destroys the now-converted basket. `BasketItemsController`/`BasketVouchersController` are the basket-mutation side-controllers, each independently re-verifying in `_before_filter()` that the targeted `BasketItem`/`BasketVoucher` actually belongs to the current session's basket (403 otherwise) since these ids are guessable. `Order` itself is never edited through the public namespace — public `OrdersController` is read-only (`index`/`detail`/`finish`); all status/item mutation happens admin-side (`admin/orders_controller.php`, `order_items_controller.php`, `order_order_statuses_controller.php`).

**Delivery configuration layering (`DeliveryMethod`, `DeliveryMethodCountrySpecification`, `ShippingCombination`, `Region`):** a `DeliveryMethod` has one base price/VAT/code, but `DeliveryMethodCountrySpecification` (keyed by `delivery_method_id` + ISO `country`) can override any of `price_incl_vat`/`vat_rate_id`/`code` per destination country — `_getSelfOrProxy()` falls back to the parent `DeliveryMethod`'s own column whenever the specification's value is `NULL`, so an admin only fills in the fields that actually differ for that country (downstream carrier integrations key off the resulting per-country `code`). Which `(DeliveryMethod, PaymentMethod)` pairs are offered together is a separate many-to-many, the `shipping_combinations` table, managed through `ShippingCombination`'s static methods rather than instance methods on either side; `ShippingCombination::GetAvailableMethods4Basket()` is the run-time facet filter `Basket::canOrderBeCreated()` calls — it narrows by region, required/excluded product tags on both delivery and payment methods, cash-on-delivery eligibility (blocked by gift vouchers or digital products), and whether an online-payment gateway is mandated, then intersects the surviving delivery methods against the surviving payment methods via the join both ways. `Region` is the top-level configuration scope (`regions` jsonb columns on `DeliveryMethod`/`PaymentMethod`/`Campaign`, read via `TraitRegions`) that also fixes a region's allowed `delivery_countries`/`invoice_countries`, default currency, and languages — switching a basket's region (`Basket::setRegion()`) silently clears its delivery/payment method selection since those are region-scoped and can't be safely carried over.

**Delivery services and pickup points (`DeliveryService`, `DeliveryServiceBranch`):** a `DeliveryMethod` can optionally reference a `DeliveryService` (e.g. a parcel-locker network) via `delivery_service_id`, which flags it as a pickup-point-style method rather than door delivery (`Basket::deliveryToDeliveryPointSelected()`). `DeliveryServiceBranch` rows are that service's actual pickup points, bulk-synced from a carrier feed by `DeliveryService::UpdateBranches()`/`importData()` (dispatched to a per-service `DeliveryService\BranchParser\<Code>` class resolved from the service's own `code` column, mirroring the `ObjectField`-style name-derivation convention used elsewhere); branches missing from a re-imported feed are soft-deactivated (`active=false`), not deleted. Once a branch is chosen at checkout it isn't stored as a foreign key — `Basket`/`Order` persist it as opaque `delivery_method_data` JSON (`external_branch_id` + a `delivery_address` sub-object), and `Basket::getDeliveryServiceBranch()` re-resolves the live row from that JSON on demand, discarding it if the JSON's embedded `delivery_service_id` no longer matches the currently-selected delivery method's (e.g. the method changed after the branch was picked). `DeliveryService::canBeUsed()` gates a service (and transitively any method/combination referencing it) on whether its feed URL's `{API_KEY}` placeholder has actually been substituted from a `SystemParameter` — an unconfigured carrier integration silently disables itself rather than erroring.

**Payment gateways (`app/models/payment_gateway.php`, `payment_method.php`, `payment_status.php`, `payment_transaction.php`; `app/controllers/payment_gateways_base.php`, `comgate_controller.php`, `go_pay_controller.php`, `gp_webpay_controller.php`, `pay_u_controller.php`, `test_payment_gateway_controller.php`):** every external gateway controller extends `PaymentGatewaysBaseController`, reached only via `GenericRouter`'s catch-all (these are machine callback URLs, not SEF ones). The base's `_before_filter()` logs every raw request (gateways POST opaque payloads), and its `_finish_transaction($options)` template method derives `gateway_code` from the controller's own class name, resolves the `PaymentTransaction` from a request param or the session, then delegates to `$pt->getPaymentGatewayApi()->updateStatus($pt)`. The gateway-specific HTTP/signature work lives one layer deeper in `lib/payment_gateway_api/payment_gateway_api.php` (`PaymentGatewayApi` namespace), whose `final` orchestration methods `startTransaction()`/`updateStatus()` call subclass-implemented hooks — `PaymentGateway::getPaymentGatewayApi()` derives the matching class straight from its own `code` column (e.g. `gp_webpay` → `PaymentGatewayApi\GpWebpay`), so adding a gateway means adding a `payment_gateways` row plus a matching API class. `PaymentMethod` is the customer-facing checkout option, optionally pointing at a `PaymentGateway` (`isOnlineMethod()` is true whenever a gateway is set and it isn't a bank transfer, since even a bank transfer can be processed through a gateway). `PaymentStatus` is a fixed, non-admin-editable three-code codebook (`pending`/`paid`/`cancelled`); `PaymentTransaction` is the per-attempt log row tied to one `Order` + one `PaymentGateway`, with retries preserved via `copyIntoNewTransaction()` (capped at 10) rather than mutated in place. `PaymentTransaction::setNewPaymentStatus()` is the single choke point pushing a payment-status change onto the order (`pending/paid/cancelled` → order statuses `waiting_for_online_payment`/`payment_accepted`/`payment_failed`), guarded to only fire from the right current order state and to assert the order isn't already paid before crediting, preventing double-credit from a duplicated webhook. Each gateway's callback shape differs (async webhook vs. signed-token browser-return vs. GoPay's `_try_to_create_missing_payment_transaction()` workaround for a known quirk where GoPay reports a transaction ATK14 never recorded) but all converge on that same `updateStatus()` choke point; the public `payment_transactions_controller.php` is the hand-off hub (`start()` redirects to the gateway's hosted page, `finish()` is the universal return point every gateway redirects to). Separately, `payment_qr_codes_controller.php` generates a bank-transfer "QR platba" PNG via `lib/payment_qr_code_generator.php` (wrapping `shoptet/spayd` + `bacon/bacon-qr-code`) from the order's `BankAccount`, usable as a fallback payment option independent of which payment method was actually selected.

**Pricing & price lists (`price_finder.php`, `pricelist.php`, `pricelist_item.php`, `product_price.php`, `product_price_before_discount.php`, `special_pricelist.php`, `special_pricelist_item.php`, `user_special_pricelist.php`, `customer_group.php`, `trait_price_manipulation.php`, `currency.php`, `currency_rate.php`, `vat_rate.php`, `vat_number.php`):** the entry point is `PriceFinder::GetInstance($user, $currency, $current_date)` (memoized by argument combination; `GetCurrentInstance()` gives a request-scoped default), whose `getPrice($product, $amount, $options)` returns a `ProductPrice`. Internally one batched, N+1-avoiding query UNIONs three sources — the user's main `pricelist`, their optional `base_pricelist`, and any `special_pricelist_items` they're granted (a flat override or a `discount_percent` off the main list) — then picks the cheapest price per quantity tier, with the main pricelist tie-breaking in its favor. `Discount::GetDiscountDataForProduct()` layers a further category/product-level markdown on top inside `ProductPrice::getRawUnitPrice()` (skipped for base-price computation). `TraitPriceManipulation` (`_removeVat()`/`_addVat()`/`_roundInternal()`) is a shared VAT-math mixin used across `PriceFinder`/`ProductPrice`/`PricelistItem`/`SpecialPricelistItem`, since each pricelist independently flags `containsPricesWithoutVat()`. B2B-style pricing tiers are per-user, not per-`CustomerGroup`: `User` carries its own `pricelist_id`/`base_pricelist_id` and a `UserSpecialPricelist` join table granting access to any number of `SpecialPricelist`s; `CustomerGroup` instead gates *eligibility* for `DeliveryMethod`/`PaymentMethod`/`Campaign`, combining explicit assignment with two implicit, never-persisted groups (`"unregistered"`/`"registered"`) synthesized in `User::getCustomerGroups()`. `ProductPriceBeforeDiscount` is not a snapshot table but a thin `ProductPrice` subclass overriding `getRawUnitPrice()` to return the pre-discount figure, giving the "was X, now Y" strikethrough. Multi-currency: `Currency::GetDefaultCurrency()` is the storage currency for all pricelist data; `CurrencyRate::GetCurrencyRate()` looks up the latest rate on or before a date, expressed *relative to the default currency* (which conventionally has rate `1.0`), with `Currency::roundPrice()` applying per-currency decimal precision at render time. VAT is per-product, not per-country: `VatRate` is a simple admin-managed codebook referenced by `products.vat_rate_id`; `VatNumber` is a `Dictionary`-based value/carrier object (backing `VatNumberField`) holding a VAT number plus a tri-state cross-border-validity flag, intended to carry a VIES lookup result rather than perform the validation itself.

**Discounts, vouchers, campaigns & promotions (`discount.php`, `voucher.php`, `basket_voucher.php`, `order_voucher.php`, `campaign.php`, `basket_campaign.php`, `order_campaign.php`, `card_promotion.php`):** `Voucher` is the customer-typed coupon-code mechanism — `voucher_code` auto-generates a collision-checked code unless supplied, and `isApplicable($basket, &$error_msg)` is the single gate a code must pass (active window, repeatability/prior-use via `order_vouchers`, region eligibility, minimum basket value); a voucher can even originate from a prior purchase as a gift card (`isGiftVoucher()`/`getOriginatorOrderItem()`). `Campaign` is the opposite: no code, no customer-facing "apply" action — it's auto-discovered by `Basket::_filterOutInappropriateCampaigns()` against conditions baked into the row itself (`getRequiredCustomerGroup()`/`getRequiredDeliveryMethod()`/`getRequiredPaymentMethod()`, tag include/exclude lists). Both share a discount shape of `discount_percent` XOR `free_shipping` (DB CHECK), `Voucher` additionally allowing a flat `discount_amount`; the unrelated `Discount` model is a per-product/per-category percentage markdown resolved via a category-tree walk (a sale/clearance feature, explicitly excluded from voucher/campaign stacking once a product is already `discounted()`). The Basket→Order mirroring for vouchers/campaigns rides inside `Basket::createOrder()`, snapshotting `discount_amount`/`vat_percent` as frozen columns on `OrderVoucher`/`OrderCampaign` (since the voucher/campaign could later change or be deleted); `BasketCampaign` is notably *not* a persisted record — it's a plain in-memory value object recomputed each request, while only `OrderCampaign` becomes a real row at order-creation time (a campaign with a gift product gets a zero-price `OrderItem` linked via `OrderCampaign.gift_order_item_id`). Percentage discounts don't simply stack — `ApplicationHelpers::GetPercentageDiscountApplicableOnBasket()` lets only the single highest-percent voucher/campaign apply across the whole basket — while flat `discount_amount` and `free_shipping` stack independently of that rule. `CardPromotion` is unrelated to all of this pricing machinery: it extends `Iobject`, making it a content/marketing object following the generic attachable-iobject pattern rather than a discount mechanism. Admin-side, `order_vouchers_controller.php`/`order_campaigns_controller.php` are full CRUD, letting an admin retroactively attach/edit/remove a voucher or campaign on an already-placed order (requiring a manual `$order->recalculatePriceToPay()` afterward since the discount is a frozen snapshot) — whereas the public `basket_vouchers_controller.php` only implements `destroy()`.

**Customer reviews (`customer_review.php`, `customer_review_history.php`, `customer_review_star_row.php`, `customer_review_status.php`, `product_customer_review_candidate.php`):** `CustomerReview` uses `TraitObjectWithStatus` (the same status-machine mixin pattern as elsewhere), giving it a status (`CustomerReviewStatus`, codebook+`Rankable`+`Translatable`) and an audit trail (`CustomerReviewHistory`, via `TraitStatusHistoryItem`). `CUSTOMER_REVIEWS_AUTOMATIC_PUBLICATION` (default true) auto-flips a review from `new` to `published` the moment it has a non-empty body, so admin moderation is opt-in exception-handling rather than gatekeeping by default. `CustomerReviewStarRow` is a per-star-value DTO built by `CustomerReview::GetStarRowsFor($card)` to drive the "5★: 80%, 4★: 15%…" histogram bar, not a per-criterion rating. `ProductCustomerReviewCandidate` is an unpersisted value object (`GetInstancesByUser($user)`) finding products from the user's successfully-finished orders not yet reviewed, driving "you can review these" prompts; `CustomerReview::CanUserReviewProduct()` is the actual eligibility check (admin, existing reviewer, or a successful order containing the product).

**Warehouse / stock (`warehouse.php`, `warehouse_item.php`):** multiple `Warehouse` records can exist, with `applicable_to_eshop` flagging which ones count toward public-facing stock (`Product::getStockcount()`'s default aggregation only sums those). Stock itself lives in the `warehouse_items` join table; `Warehouse::addProduct($product, $delta)` does an atomic upsert via a PL/pgSQL exception-handling block rather than application-level locking. Available-to-order quantity (`Product::getMaximumQuantityToOrder()`) is stockcount minus a hidden-stock reserve (keyed by product or by category+unit fallback) minus reservations from unfulfilled orders — `consider_stockcount` on the product can disable stock-limiting entirely.

**Favourites vs. watched products (`favourite_product.php`, `favourite_products_accessor.php`, `watched_product.php`):** two distinct features. `FavouriteProduct` is a wishlist entry, always accessed through `FavouriteProductsAccessor($user, $session)`, which transparently unifies logged-in storage (by `user_id`) and anonymous storage (a random `session_salt` kept in the session, scoping `favourite_products` rows by that salt instead) so a guest's wishlist survives across requests without an account. `WatchedProduct` is a "back in stock" notification signup (tied to a `user_id` or a bare email for guests, with `notified`/`notified_at` flags) — an unrelated mechanism driven by a robot querying `WatchedProduct::GetWatchedProductsToNotify()` against current stock.

**Digital content (`digital_content.php`, `digital_content_download.php`):** a `DigitalContent` is a downloadable file tied to a `Product`, stored outside the DB under `DIGITAL_CONTENTS_DIRECTORY` and sharded by `<year>/<month>/<id>.dat`, region-gated the same way delivery/payment methods are (`TraitRegions`). Access is token-based rather than login-gated by default: both `Order` and `DigitalContent` issue HMAC-style tokens derived from `SECRET_TOKEN`, combined into a download URL (`DigitalContent::getDownloadUrl($order)`); the controller additionally requires the logged-in user to match the order's owner if the order has one. Every download is logged as an append-only `DigitalContentDownload` row for auditing, not to enforce a download-count limit.

**Cookie consents (`cookie_consent.php`, `cookie_consent_category.php`):** `CookieConsent` is a de-facto singleton (`GetInstance()` hardcodes id `1`) holding the banner copy; `CookieConsentCategory` is the admin-managed set of consent buckets (e.g. "necessary", "advertising"), with `necessary` categories hardcoded non-deletable. Per-visitor consent state isn't stored in either model — it's delegated to `CookieConsentSettings` from the separate `atk14/cookie-consent` package (`CookieConsent::GetSettings($request)`/`Accepted($category_code)`); the public controller just reads/mutates that settings object and fires a structured log line on every save, which `local_scripts/export_cookie_consent_statistics` turns into a CSV for the admin statistics view rather than querying a database table.

**Creators (`creator.php`, `creator_role.php`, `card_creator.php`):** `Creator` represents a person (author, illustrator, translator, …), distinct from `Brand`, optionally linked to a `Page` for a bio. `CreatorRole` is the admin-managed lookup of relationship types (e.g. "Author", "Illustrator"). `CardCreator` is the card↔creator↔role join row, with an `is_main_creator` flag picking which creator(s) headline the card — batch-loaded the same `CacheSomething` way as technical specifications. Unlike `category_cards`/`collection_cards`, this bridge follows the pattern only partway: `admin/card_creators_controller.php` has no `index` (the list is inline on the card edit view), and `admin/creators_controller.php` itself has only `edit`, no `create_new`/`index`/`destroy` — new creators are expected to originate elsewhere (e.g. alongside a `Page`) rather than through a dedicated admin list.
